Ten tables. The three across the top are the question spine — a scraped sighting, the question it is a sighting of, and one row per month that question appeared in. Everything a user or an editor touches attaches to the middle one, which is what makes a label or a tick follow a question across every month it recurs in.

Why this split is the whole design. Before it, one table was both the identity and the timeline entry: when a question recurred, its id moved to the newest month and the old row was left behind unlabelled — 49 times. Now a question that ran for eighteen months is eighteen list_questions rows sharing one fingerprints row, so it carries one set of labels and one practised state.

Two deliberate loosenesses. f_id is nullable because an uploaded file may name a question the database does not have, and dropping those rows silently would make the counts lie. decision is text rather than a foreign key because a reviewer must be able to write a label the vocabulary lacks — resolution happens at apply time, where what could not be resolved is reported instead of invented.

Everything a user or an editor touches hangs off fingerprints — labels, progress, bookmarks and review items all point there, never at list_questions. That single choice is what makes the timeline a presentation layer rather than a source of truth.

Derived columns are recomputed, never incremented. months_seen, total_sightings and month_sightings are recalculated from the rows that exist, so an import that overlaps an earlier one cannot double-count.
