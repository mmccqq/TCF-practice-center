1 Plan

Re-read each site's index, list every month page, and subtract the periods already in raw_questions.

The newest two months are always re-fetched — a site keeps adding questions to the current month after publishing it.

≤ 12 pages / run1s between requests

2 Fetch & parse

Each page is fetched, parsed in memory, and thrown away. Only the questions are kept.

Per question: text, task 2 or 3, exam month, part, subject number, and where it came from.

no HTML storedprogress per page

3 Fingerprint

Normalise the wording — case, accents, spacing, punctuation — and hash it. Two sites writing the same question differently land on one hash.

Scoped by task: the same sentence under Task 2 and Task 3 is two different questions.

SHA-256

4 Load, three layers

Group by (task, hash). Write the question, then its sightings, then one row per month it appeared in.

Counts are recomputed from the rows that now exist, never incremented.

dry run firstre-runnable
Why nothing is cached on the server. A parse is a pure function of one page, and the host wipes its disk on every restart — a cache there would be rebuilt from nothing each run. Which months exist is already recorded in the data, so the database is the cache. A routine run fetches one page, not the hundred-odd in the archive.
Why re-running is safe. Every write is keyed on something the source already decided — the scraper's own id, the hash, the month — so an import that overlaps an earlier one finds its rows already there. This is what lets the import be a button rather than a procedure.

5 Choose the questions

Filter by task, theme, or what is missing — or tick rows and select all that match.

A job defaults to questions that lack the field it is about: relabelling what is already labelled is the expensive way to change nothing.

themeabstractcore subject

6 Ask one or two models

Questions go out in chunks. Each reply is checked position-by-position against the ids that were sent, so a shifted answer is caught rather than written to the wrong question.

Keys are typed into the dialog and passed as arguments — never stored on the job, logged, or returned.

OpenAI · DeepSeek · Gemini · Anthropic

7 Merge into one batch

Both models' answers land on the same review item, so an item carries {model: answer} and a disagreement is visible without a second pass.

The batch is created before the first call: a job that dies at chunk 5 of 8 still leaves five chunks reviewable.

resumable by inspection
Why two models instead of a better prompt. A single model labelled themes correctly about 85% of the time against a hand-built gold set. Filtering to where two models independently agree raises that to 90–92% — and, more usefully, it sorts the work: the ~10% they split on is exactly the set worth a person's attention.

Review the only step with a person in it

8 Accept the agreed

One click takes the answer wherever every run gave the same one — about 90% of a theme batch.

An item with a single candidate is left alone: one run agreeing with itself is not agreement.

9 Adjudicate the split

The reviewer sees the question, each model's answer, and how many other questions already sit under each candidate.

They may type a label the vocabulary does not have — the decision is free text until it is applied.

10 Apply

Names are resolved to vocabulary rows and written onto the questions. Applying twice is safe.

Anything that could not be resolved comes back as unresolved, with its count and the theme it would need — not silently dropped, and not invented.

LOOP

Unresolved labels feed the vocabulary, then the batch is applied again. On the first full pass this surfaced 63 labels the models had invented; 31 named something real and became new core subjects, and the rest were wrong. Refusing to auto-create them is what keeps the vocabulary from drifting into 400 near-synonyms.

Serve public pages · computed from the same tables, no export step

11 The month list

Questions grouped into year-month sections, newest first, loaded as the reader scrolls. Each card shows its theme and core subject.

12 The core set

Labelled questions grouped by theme and core subject; a subject joins the set once two or more distinct questions share it, ranked by how many separate exam months it spans.

One representative question is shown; the rest expand in place.

13 Progress

A tick is stored against the question, not the month row — so it marks that question practised in every month it appears in, and it survives the next re-scrape.

Progress counts core subjects, not cards.

No publish step, by design. The public pages read the same three tables the admin writes, so applying a batch is live immediately; the only thing between the two is a 60-second browser cache, which an admin edit invalidates explicitly.

Every stage is re-runnable and every stage reports what it did. Intake dry-runs before it writes, a labelling job survives its own death, and apply names what it could not resolve. Nothing in this pipeline is a one-shot script whose output you have to trust.

The expensive stage is bounded on purpose. One job at a time, at most 600 questions, chunked — so a mistyped filter costs a few cents rather than an afternoon's budget.
